## Findings requiring attention

### SC-A - Central register records source pointers without semantic claims

The [central JSON register](../../source-registers/skills-engine-currentness-2026-09.json) declares a policy requiring claim-specific support review, but its claim objects supply identifiers, a currentness flag, and source IDs without claim text or `support_review`. The ASVS row does not record the stable edition actually admitted. Source freshness values such as `current`, `platform`, and `regulatory` also differ from the classes defined by the [mandatory gate](C:/wamp64/www/digital-research-skills/docs/continuous-improvement/kaizen-currentness-gate.md). This is a schema/meaning mismatch, not evidence that every referenced source is false (synthesis).

The inspected [CI workflow](../../../.github/workflows/skill-guardrails.yml) runs catalogue, source-ingestion, routing, and control-plane checks; it does not invoke a claim-source currentness or semantic-support verifier. The [catalogue checker call list](../../../scripts/skill_catalog_guardrails.py) likewise lacks that check. Other enforcement paths are NOT ASSESSED; do not infer their absence throughout the portfolio.

Action: before a central claim authorises guidance, supply exact wording, scope, edition, locator, reviewer, support state, confidence, and uncertainty. Align freshness vocabulary explicitly. Add a currentness check with expired, missing-claim, missing-review, and unsupported-source fixtures. A working URL and future review date must not be treated as semantic approval.

### SC-B - Local portability validation rewards a conflicting metadata shape

The [compliance scanner](../../../skills/sdlc-meta/skill-engine-audit/scripts/engine_compliance.py), in `portable_metadata` and `safe_fix`, requires a boolean `portable` and list-valued `compatible_with`. The [audit skill itself](../../../skills/sdlc-meta/skill-engine-audit/SKILL.md) uses that shape. The external [Agent Skills metadata contract](https://agentskills.io/specification) specifies string values. The local contract therefore does not demonstrate conformance to the public interchange specification (synthesis).

Action: distinguish a documented local extension from the interchange format; choose a conforming representation or explicit export transformation and version its schema. Validate a representative exported skill with the reference validator, then test loading and a task in each intended host. Runtime rejection is NOT ASSESSED; no rejection is invented here.

The [catalogue checker](../../../scripts/skill_catalog_guardrails.py) imposes its own description-length policy, and the [routing smoke test](../../../scripts/routing_smoke_test.py) describes its lexical approach as a proxy. Preserve useful local constraints, but label format, house style, routing proxy, real host behaviour, and downstream output quality separately. Local compliance scores must not be relabelled as production or universal portability scores.

Concurrent repair note: the parent reported divergent description limits while this report was being prepared. At this workstream's final inspection, [skill-writing prose](../../../skills/sdlc-meta/skill-writing/SKILL.md), [quick_validate](../../../skills/sdlc-meta/skill-writing/scripts/quick_validate.py), [catalogue policy](../../../scripts/skill_catalog_guardrails.py), and [compliance trigger validation](../../../skills/sdlc-meta/skill-engine-audit/scripts/engine_compliance.py) each specified a **350-character** repository limit. The public format permits descriptions up to **1024 characters**, per the [Agent Skills description field](https://agentskills.io/specification). The stricter repository rule is compatible with that outer format limit; it is not a host runtime-budget measurement. The observed description inconsistency is therefore structurally repaired by concurrent work, with boundary-test behaviour NOT ASSESSED here. This does not close the separate metadata-shape finding above.

### SC-C - Pipeline guidance uses a historical DORA baseline as current

The [pipeline observability reference](../../../skills/devops-cloud/cicd-pipelines/references/pipeline-observability.md) and [pipeline skill](../../../skills/devops-cloud/cicd-pipelines/SKILL.md) present the older metric set as canonical. The reference uses general incident MTTR and omits deployment rework rate. Compare BENCH-DORA and the [current definitions](https://dora.dev/guides/dora-metrics/): this is a substantive definition mismatch (synthesis).

The local target table supplies fixed lead-time, failure-rate, recovery, queue, stage, and cache thresholds without a claim-specific source or a project baseline in that reference. Their authority as universal engineering benchmarks is NOT ASSESSED; no source found for that universal interpretation in the inspected evidence. Action: mark them as locally proposed budgets, require workload/owner acceptance, and revise measurement definitions and event lineage. Retain general incident recovery as a separate operational measure. Include incident-triggered rework and deployment-failure recovery in the evidence schema (inference).

### SC-D - Security references mix editions and do not establish verification coverage

The [vibe-security mapping](../../../skills/security/vibe-security-skill/references/owasp-mapping.md) names the newer edition. However, [input-validation references](../../../skills/security/web-app-security-audit/references/input-validation-patterns.md) retain **A03 Injection / A05 Security Misconfiguration**, and [business-logic references](../../../skills/security/web-app-security-audit/references/business-logic-flaws.md) retain **A04 Insecure Design**, without edition qualifiers at those citations. Those identifiers do not match the opened [OWASP edition/category list](https://owasp.org/Top10/2025/0x00_2025-Introduction/) (synthesis). This finding concerns identifiers, not the validity of every code example.

Action: version every category citation and either preserve it as historical or migrate it using an explicit mapping. For actual verification claims, bind selected ASVS requirements, applicability decisions, test evidence, exceptions, and reviewer disposition to the release. The [delivery template](../../../templates/delivery-dod/evidence-pack.md) currently asks for OWASP-relevant checks and scans but does not itself require version-qualified requirement coverage. Useful security prose is not proof of a completed verification (inference).

### SC-E - Maintenance guidance needs edition selection and narrower compliance claims

The [maintenance reference](../../../skills/sdlc-meta/sdlc-documentation/references/sdlc-maintenance.md), particularly its SMP structure and required-sections passages, promises standards compliance and a mandatory clause structure. BENCH-LIFECYCLE establishes a newer published lifecycle edition; BENCH-MAINT also shows why the maintenance document's older relationship cannot simply be called erroneous (synthesis).

Action: add an explicit project baseline/edition decision and a currentness row for lifecycle and maintenance standards. Keep historically correct relationships qualified. Quarantine the exact subsection mandate and automatic compliance wording until an authorised normative locator and a reviewer mapping are available. Do not substitute a remembered clause list or silently update the year. Public status verification has not established clause-by-clause compliance.

### SC-G - Engineering benchmarks need a source-to-acceptance mapping

The inspected [source-register directory](../../source-registers/) contains ASVS and accessibility pointers, but no named SSDF, SLSA, DORA, ISO product-quality, or Agent Skills benchmark records. The [engineering gates](../../../skills/sdlc-meta/world-class-engineering/references/world-class-gates.md) and [delivery pack](../../../templates/delivery-dod/evidence-pack.md) provide useful release and recovery prompts; they do not supply those benchmark mappings themselves. No claim is made that the entire catalogue lacks the underlying practices.

Action (inference): add an engineering benchmark register that pins each adopted standard to its precise scope, version/status, source, review trigger, applicable control, expected artifact, and acceptance decision. SSDF can frame secure-development practices; SLSA can frame a named supply-chain assurance target; ISO product quality can frame explicit quality criteria. These are proposed uses of BENCH-SSDF, BENCH-SLSA, and BENCH-QUALITY, not certifications or mandatory adoption of every standard.

The delivery pack also names commercial/industry benchmark inspirations without linking specific supporting artifacts in that template. Treat those attributions as unverified inspiration until precise primary-source mappings are attached, or remove the implied authority. No source found in the inspected template for the claimed mapping; no external organisational practice is inferred from the names.
